# Changelog

All notable changes to Covia are documented here.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and the project aims to follow [Semantic Versioning](https://semver.org/spec/v2.0.0.html).
Covia is pre-1.0, so minor versions may include breaking changes.

## [Unreleased]

### Added
- **Secrets can be deleted (#166).** `covia:delete path=s/<name>` removes one of the caller's own secrets — whole records only (deeper paths are rejected: partial deletion inside an `{encrypted, updated}` record is never meaningful), idempotent, capability-pinned as `crud/delete` on the exact path so the public read-only ceiling denies it. No new op: the existing CRUD surface is extended, and `s/` stays delete-only (`covia:write`/`append` still reject it — records are created exclusively through `secret:set`'s encryption). Deletion is merge-safe by construction under the whole-value-LWW venue node below, so consumers can drop the empty-value tombstone workaround.
- **Venues are strictly did:web-resolvable (#167).** When a venue has a public `hostname` configured, `/.well-known/did.json` is served under its did:web alias — `id: did:web:<hostname>` with the canonical did:key in `alsoKnownAs` and the same Multikey verification method — so conforming resolvers (e.g. `web-did-resolver`, the TS SDK) pass the DID-Core id-match check. **did:web is discovery, not identity**: the venue's canonical ID stays did:key everywhere durable (lattice keys, UCAN issuer, signatures, `status.did`, asset DID URLs), so a domain change or lapse cannot break stored state — trust flows domain → did:key at discovery, then everything pins the did:key. The host comes from config, never from spoofable `X-Forwarded-*` headers, and localhost/IP/host:port hostnames never claim a did:web identity. JWT `aud` accepts the alias alongside the did:key, since strictly-resolving clients audience tokens to the DID they resolved.
- **`POST /invoke` takes a millisecond wait window, and the transport contract is documented (#140).** `wait` now follows the same convention as the op-level `wait` on `agent:request`/`agent:trigger`: absent/`false` = asynchronous (201 + job record to poll — the default for *every* operation, which is what #140 actually observed); `true` = block up to the 120s cap; an integer = block up to that many milliseconds (clamped to the cap — a waiting request holds a server thread, so the cap is a resource guard). On expiry the current record returns (201) and the caller keeps polling. A malformed `wait` is rejected with 400 *before* the operation is invoked, so a bad request creates no orphaned job. The `/invoke` OpenAPI reference now spells out the whole contract, including that meta-operations like `grid:job-result` complete their local job with the remote result (with an op-level `timeout` input for bounded waits).
- **Optional output-schema validation (#51).** A venue config setting `outputValidation` — an *operator* decision — checks a completing one-shot job's result against the operation's declared `output` schema: `off` (default — no validation, no logging), `warn` (log a mismatch), or `strict` (fail the job). Off by default, so nothing is validated or logged unless an operator opts in (no automatic warnings). This complements the per-operation `strict` flag that governs *input* validation (the operation author's contract); output validation is a venue-level policy and a regression guard — e.g. it can enforce the CRUD output shapes from the change above. Applies on the default one-shot completion path; reuses `JsonSchema`.
- **Three new first-class LLM providers: Google Gemini, xAI, and DeepSeek (#158).** Installed as `v/ops/langchain/gemini`, `v/ops/langchain/xai`, and `v/ops/langchain/deepseek`, each with a dedicated provider case in `buildProviderModel` carrying the correct default endpoint and model — Gemini `gemini-2.5-flash` (via Google's OpenAI-compatible route), xAI `grok-4` (`api.x.ai/v1`), DeepSeek `deepseek-chat` (`api.deepseek.com/v1`) — and its own per-user secret (`GOOGLE_API_KEY` / `XAI_API_KEY` / `DEEPSEEK_API_KEY`). Each op dispatches to its own `langchain:<provider>` adapter rather than the generic OpenAI route, so routing is unambiguous.
- **Configurable HTTP bind address (#129).** A new `bindAddress` venue config key is plumbed through to the Jetty connector (`connector.setHost`). The connector previously always bound all interfaces (`0.0.0.0`); embedders that spawn the venue as a local subprocess can now pin it to `127.0.0.1`. Unset preserves the existing `0.0.0.0` behaviour. `bindAddress` (the socket bind) is intentionally distinct from `hostname` (the advertised public host); the resolved bind address is logged at startup.
- **Configurable venue-wide agent defaults.** `AgentAdapter` create-time defaults now read `Config.getDefaultLlmOperation()` / `getDefaultTransitionOp()` instead of hardcoded constants, so an operator can set the default LLM and transition op for a venue.
- **Build version in the `/status` response (#139).** `Engine.getStatus` now reports the shaded jar's `Implementation-Version` (or `"dev"` when running from classes; never null), so operators can detect build/version drift across venues.

### Changed
- **The venue lattice is a single navigable whole-value-LWW node — deletions are durable venue-wide (requires the upcoming Convex 0.8.7).** The venue `:value` now carries a wall-clock `:timestamp`, re-stamped on every write by Convex's new stamp-on-write lattice layer; merge picks the newer whole value (tie → own, non-recursive), so a deletion is part of the winning value and survives the propagator's merge-back, persisted reload, and replica restore *by construction*. The interior (`:assets`, `:storage`, `:did`, `:users`, `:schedule`, `:user-data`) is plain navigable JSON, merged only at the root — correct because a venue has a single authoritative writer (its signing key), so every merge is a stale-vs-fresh snapshot of the same lineage. This generalises the 0.2.0 durable-delete fix from three namespaces to the whole venue: agent hard-delete, schedule removals and secret deletion now also survive merges. All per-entry LWW plumbing is removed (`LWWWrapperLattice`, `AGENT_LWW`, `max(now, current+1)` stamp inflation); `w`/`o`/`h` keep their `{updated, data}` storage shape with `updated` now stamped by the lattice itself. **Existing venue data loads unchanged** (children keep their paths and shapes; migration ≈ nil) — verified live on the dev venue fleet, including restart survival. Until Convex 0.8.7 ships, develop pins `convex.version=0.8.7-SNAPSHOT` and all CI build workflows compile Convex from source (a step that skips itself once the pin returns to a release). Design: `venue/docs/GRID_LATTICE_DESIGN.md` §A.2.
- **LLM tool-call arguments are parsed once, at the wire boundary — internal dispatch never coerces (#89, #58).** The policy: be generous with LLMs (external systems whose output we cannot force to be well-formed) but *only* at named wire boundaries; everything internal preserves types exactly. A new `parseToolArguments` replaces the old scattered `ensureParsedInput`: absent → empty map, already-structured arguments pass through (fixing a real bug — providers delivering arguments as objects were silently dropped to an empty map), JSON strings are parsed, double-encoded strings get one more pass, and outright garbage produces a *visible* tool error the LLM can correct on its next turn — never a silent empty-map invocation. Internal dispatch passes inputs through exactly as given, so the config-mapped and grid-dispatched tool paths are behaviourally identical (previously the same tool call could store a string on one path and a map on the other, failing intermittently).
- **`schema:*` operations process the value exactly as given.** A JSON-looking string IS a string: it passes `{"type":"string"}` and fails `{"type":"object"}` — previously a silent reparse meant a legitimate string could wrongly fail validation, or a caller's broken JSON could validate as `true`. A string-encoded `schema` parameter is still accepted (LLM callers stringify), but a malformed one now reports its real parse cause instead of the misleading "'schema' is required".
- **Adapter asset installation fails loudly.** A missing or unreadable adapter resource now fails venue startup (a packaging bug — the venue would otherwise boot with silently missing ops), matching the fail-loud ops-catalog materialisation. A new `strictAssets: false` config downgrades this to warnings, for test/debug scaffolding only.
- **Upgraded to Convex 0.8.6 and migrated the venue HTTP layer to Javalin 7 / Jetty 12 (#152).** Convex 0.8.6 bumps Javalin 6.7 → 7.2.2 (Jetty 11 → 12), a breaking change adopted to keep covia in sync with the latest Convex release. All handler registration moves off the Javalin instance onto `config.routes` at create time (`addRoutes(RoutesConfig)` across CoviaAPI, A2A, UserAPI, CoviaWebApp, MCP, AuthMiddleware); virtual threads move to `config.concurrency`; the OpenAPI plugin uses the fluent `definition.info(...)` API; Jetty 12's relocated session classes are handled by registering a no-scavenge `SessionIdManager` bean. Jetty 12's default `UriCompliance` rejects encoded slashes (`%2F`), which broke percent-encoded catalog-name lookups (`GET /api/v1/operations/v%2Fops%2F…`) and the cross-venue named references built on them — the connector now opts back in via `UriCompliance`, matching Jetty 11 (a cleaner long-term fix is tracked in #153).
- **Upgraded the MCP SDK to 2.0.0 (#156)** and the **A2A SDK to 1.0.0.Final (#155).** These are dependency majors; downstream embedders that pin these transitively should retest. A unit test now covers the MCP client bearer-auth customizer (#157).
- **Agents are strict-allowlist by default (#92).** `ContextBuilder.withTools()` previously appended an 18-op default tool pack (incl. `covia/inspect`, `covia/delete`, `agent/create`) to every agent unless `defaultTools: false` was set. An agent is now advertised exactly the tools it declares in `tools`, and opts into the default pack with `defaultTools: true`. This is fail-safe — a newly-authored agent no longer silently receives ops it never declared (the foot-gun that let a scoped agent reach `covia_inspect` on the lattice root). Capability enforcement is unaffected (caps come only from the config's explicit `:caps`); only which tool schemas are advertised to the LLM changes. All bundled configs already set `defaultTools` explicitly, so none change behaviour. (#134)
- **`covia:write` requires a `value`; path-only writes are rejected.** A missing `value` key was treated the same as an explicit null, so a tool call supplying only `path` silently created a null entry — and the model, seeing a misleading `pathCreated: true`, looped re-writing it. An absent `value` now throws so the caller retries with the value; an explicit `null` is still accepted as the documented delete semantics (distinguished via `containsKey`).
- **Assets can be retrieved by lattice address, not just hex hash (#150).** A new venue endpoint resolves lattice addresses, and `VenueHTTP.resolveAsset` uses it.
- **The default Anthropic chat operation is now `claude-sonnet-4-6`.**
- **Dependency maintenance:** logback-classic 1.5.18 → 1.5.34, FlatLaf 3.6.1 → 3.7.1, the maven-assembly-plugin, and several GitHub Actions (checkout 6 → 7, cache 5 → 6, docker/login 3 → 4).
- **Private Network Access header is off by default (#130).** The venue previously emitted `access-control-allow-private-network: true` on every response, letting a public web origin reach a venue on a loopback/private address from the browser (GetMine-ai/demo#133 P0-2). It is now gated behind a new `allowPrivateNetwork` config flag (default `false`) — enable it only for the preview-origin dev workflow that needs it. (Embedding apps authenticate with their own self-signed JWT via the existing self-issued verification path; the venue mints nothing.)
- **covia CRUD operations return meaningful values, not tautological flags.** `covia:write` / `copy` / `delete` / `append` previously returned a constant `{written|copied|deleted|appended: true}` that only restated job success. They now carry actual variables: `write` / `copy` return `{pathCreated: true}` *only* when the write had to build a missing parent path (intermediate hierarchy), omitted otherwise — and independent of whether a value already sat at the leaf; `append` returns `{newSize}` (the vector's element count after the append) plus `pathCreated` when it built hierarchy; `delete` returns an empty map — it removes only the addressed value and never prunes parent hierarchy, so there is nothing structural to report. Read-family field names are now consistent: `covia:read` reports `valueBytes` (always present; was `size`, only on truncation), `truncated` omitted when false; `covia:slice` / `list` report `totalSize` (was `count`) and always echo `offset`. Operation success remains the job's terminal status. Inputs are unchanged. (#132)

### Security
- **Capability enforcement is now active (#148).** The capability ceiling is a property of the `RequestContext`, enforced at the point of action (adapter-pinned `requireCapability`, backed by a name-keyed boundary that acts as a default-deny net). `operationAbility` maps every venue-resource mutation (covia / file / dlfs / vault writes and deletes, `asset:store`, agent-lifecycle mutations, `secret:set`) to a withheld ability rather than the generic `invoke` catch-all — drift-guarded by `CapabilityCheckerTest.testReadOnlyCeilingDeniesAllVenueMutations`. Unauthenticated callers default to a read-only ceiling (`crud/read` + `asset/read`), operator-overridable via `auth.public.caps`; ceilings compose downward into sub-operations. This activates the enforcement whose absence was reported in #141.
- **JWT audience is validated at the auth boundary (#149).** Tokens are classified as UCANs by the presence of an `att` (capability) array rather than by `aud`-presence (identity tokens now legitimately carry `aud`); the venue's `venueDID` is wired into the accepted-audience set; and self-issued tokens get 60s of clock-skew leeway on the temporal check.
- **A UCAN bearer's signature is bound to the claimed issuer**, closing an identity-spoofing gap where a presented bearer could claim an issuer it did not sign for.
- **A presented bearer token that fails verification is now a hard 401 — never a silent downgrade to the public identity.** Previously, when public access was enabled, a tampered/expired/forged token (or an unexpected exception during verification, e.g. a JWKS outage) fell through to the anonymous identity with a 200. Presenting credentials is an explicit identity claim; failing that claim is now visible to the caller under all conditions. Anonymous requests without a token still get public access; unexpected verification errors now log at warn instead of debug. The transport regression tests assert the strictly stronger contract.
- **Malformed JSON request bodies are the caller's error: 400 with the parse cause** (`/invoke`, job `sendMessage`, `putSecret`) — previously they surfaced as a generic 500 via the global exception handler.

### Fixed
- **Remote-fetch failures surface as meaningful errors instead of "not found" (#174).** The Engine's remote definition/content fetch (invoking a `did:web:…` reference, `asset:pin`/`get` of a remote ref) collapsed *every* failure — venue unreachable, venue error, corrupt/mismatched metadata, malformed reference — into a `null` that read as "asset absent", so a down venue was indistinguishable from a genuinely missing operation ("Cannot resolve operation"). The fetch layer now returns `null` **only for genuine absence** (the venue is reachable but has no such asset / does not bind the name — an expected outcome callers handle) and throws a `RemoteFetchException` naming the venue for *operational* failures. The distinction follows a clear rule: absence-as-null is fine where a caller expects it; the error is raised where the result is *used* for something that can't work with absence — a direct invoke returns HTTP **502** (the upstream fetch failed, not a 404); a job-aware adapter (e.g. `agent:create` resolving a remote `definition`) fails the **job** cleanly with the message; and aggregate callers that assemble many references (agent tool/context building) catch it and degrade **visibly** rather than fail wholesale. Logs moved debug → warn. (Deferred: `VenueHTTP.getAsset` in covia-core still folds a remote 5xx into `null` before the Engine sees it, so "reachable-but-errored" isn't yet distinct from a 404 end-to-end — a separate covia-core follow-up; unreachable / malformed / integrity are all distinguishable today.)
- **`v/`-namespace writes no longer silently no-op on startup (#159).** Since the switch from `RequestContext.INTERNAL` to `engine.venueContext()` for startup writes, `materialiseVOps()` / `materialiseVenueInfo()` had become a no-op on every restart: the static writable-namespace guard rejected `v/…` paths before the per-caller `NamespaceResolver.canWrite(ctx)` check (which authorises the venue's own DID) could run. As a result the new `v/ops/langchain/gemini` & `deepseek` ops never appeared in the lattice after deploy, and `v/info/*` (version, started, adapters) went stale. The write-access check now consults the namespace resolver first and falls back to the static allowlist only for plain namespaces.
- **Job IDs are now monotonic, so the per-user job index — and the `GET /jobs` listing built from it — is fully ordered under concurrency.** ID generation used an unsynchronised per-millisecond counter, so two submissions in the same millisecond could lose-update the counter and fall back to ordering by the random tail (IDs stayed unique, but intra-millisecond order was not guaranteed). The `(timestamp, counter)` prefix is now advanced via a single `AtomicLong` as `max(prev+1, ts<<16)`, making IDs strictly increasing — across concurrent submissions, same-millisecond bursts (the counter carries into the timestamp bits past 65535/ms), and a backwards clock step. IDs remain 16 bytes (6-byte timestamp + 2-byte counter + 8-byte random); the byte layout is unchanged.
- **An agent that exhausts its tool-call iteration limit now fails its task (#138)** instead of silently giving up.
- **A missing intermediate value is surfaced, not nulled, during path resolution** (`MissingDataException`), and a write of a named key into a list now gives a clear shape-conflict error rather than corrupting the structure.
- **Indefinite-blocking paths found in a hang audit are now bounded**, and waits on `invokeInternal` are no longer auto-timed-out — IO is bounded at the IO layer instead.
- **A deep write into a scalar no longer silently destroys it.** A `covia:write`/`covia:append` whose path navigates *through* an existing non-map, non-vector value — e.g. `w/a/b` where `w/a` holds a string — previously replaced the scalar with a map (silent data loss). It now throws a clear shape conflict naming the node (*"Cannot set key '…' on the scalar value at '…'"*), mirroring the list case fixed for GetMine-ai/demo#146. A genuinely absent intermediate is still auto-vivified; only a real value is protected. (`deepSet`/`deepAppend`)
- **A presented token's attenuation is now enforced on the direct invoke path (#131).** `CoviaAPI`/`MCP` attached a caller's UCAN proofs but never set a capability ceiling, so an *attenuated* bearer/UCAN presented to `/invoke` ran with the identity's full authority. Both transports now derive a self-attenuation ceiling and apply it via the existing `enforceCaps`. Done on the principled owner-scoped model: capability resources are absolute (owner-named), so enforcement canonicalises every resource — and each capability's `with` — to `<ownerDID>/…` before matching (`Capability.covers`), with DID-URL and `file://`/`dlfs://` resources already absolute. This unifies the self and cross-user enforcement conventions and is backward-compatible with bare agent-config caps (both sides canonicalise identically). The ceiling is **owner-authored** (the owner is the authority over its own namespace; the venue only enforces) and can only *narrow* a caller's own authority, never widen it. New convex-core primitive `UCANValidator.capabilitiesFor` is the canonical home for the selection; covia uses an interim `CapabilityChecker.selfCapabilities` (deprecated — to be removed when covia's Convex dependency includes `capabilitiesFor`).
- **An agent's run loop now executes under the agent owner's identity, not the waking caller's.** `wakeAgent` previously captured the triggering caller's `RequestContext`, so under concurrent mixed-identity wakes the loop — and every identity-scoped access during it (secret `/s/`, workspace `w/`, job ownership) — could resolve in the wrong namespace. The run loop is now a pure mechanism keyed on the agent's address (`ownerDID` + `agentId`) and runs under a fresh owner-scoped context carrying none of the waker's proofs or caps; the in-memory run-loop registries key on the full address so two users' same-named agents no longer share a slot. `Engine.resolveSecret` now distinguishes a genuinely absent secret (null) from a decrypt/key error (logged at WARN + thrown) instead of masking both as absence. (#91)

## [0.2.0] - 2026-06-15

### Added
- **User memory.** A single `memory` tool (`v/ops/memory`, dispatched by a `command`: `recall` / `remember` / `update` / `forget`) maintains a per-user numbered list of durable facts in the user's workspace — one tool definition rather than four ops, to keep agent tool context small. `recall` doubles as a `config.context` assemble-op (injected as system context every turn) and renders either a flat list or, given a `displayField`, the active/surfaceable values of a slug-keyed map collection — skipping entries whose `status` is not `active`, that are `surfacing: hold`, or that carry a `mergedInto` — so a curated store (e.g. a problem list) can be surfaced with no separate copy. Mutations rewrite the whole list value under LWW, so removals are durable. See `venue/docs/AGENT_CONTEXT.md`.
- `venue/docs/AGENT_CONTEXT.md` (renamed from `CONTEXT.md`): the agent-context design — entry forms, the specify→return→render data-shape contract, and the failure model.

### Fixed
- `covia:delete` is now durable. The user-writable namespaces (`w/`, `o/`, `h/`) previously merged per-entry (a union), so a deleted key was re-introduced whenever the live cursor merged with a pre-delete snapshot — which the persistence propagator does on every announce round-trip (deletes "came back" within ~30s and after restart). These namespaces are now whole `{updated, data}` values replaced as a unit under LWW (`LWWWrapperLattice`), the same trade the `:schedule` slot made. Write stamps are strictly increasing (`max(now, current+1)`), so fast sequential writes in the same millisecond each dominate the value they replace in either merge order. The wrapper is storage shape only — paths, reads, and lists are unchanged; pre-existing unwrapped workspace data remains readable and is migrated in place by the first write.

### Changed
- **Cross-venue reference semantics.** Invoking a `did:web:<venue>/a/<hash>` operation reference now **fetches** the content-addressed definition from the publishing venue (hash-verified) and executes it locally, as an ordinary local job — references denote definitions, never execution sites. The previous reference-inferred remote delegation (which blocked a thread and left no job record on the accepting venue) is removed; cross-venue *execution* is explicit via `grid:run` / `grid:invoke` with a `venue` argument, which records a job on each venue. Semantics pinned by `RemoteAssetFetchTest` / `RemoteOperationTest`; see `venue/docs/OPERATIONS.md` §4.
- `Grid.connect` resolves `did:web` DIDs with percent-encoded ports (`did:web:host%3A8080`) and uses http for localhost, per the did:web spec note.
- Named catalog references (`did:web:<venue>/v/ops/<name>`) resolve as fetches too: the name is resolved to an asset id at the publishing venue (names are mutable bindings, trusted at fetch time), then the definition travels over the same hash-verified path. The job record carries the resolved hash — name→hash provenance at invoke time. Fetches remain transient; pin is the explicit adoption act.
- `asset:pin` can now actually adopt remote assets: pinning a `did:web:…` reference (hash or named form) fetches the definition hash-verified — plus declared content, verified against its sha256 — and stores it durably in the caller's namespace.
- Fetched definitions are cached in memory by content hash (immutable, so never stale): repeat invokes of a remote reference no longer re-fetch, and a cached definition resolves even if the reference's venue hint is unreachable. The cache is transient plumbing, not adoption.
- **Agent context resolution fails loudly, not silently.** A `config.context` / `state.context` that is present but not an array now throws (a malformed value was previously dropped, leaving the agent with no context and no signal). A context entry that *errors* while resolving — an assemble op that throws or times out, a read that genuinely fails — now injects a visible `[Context: <label> — unavailable: <reason>]` element instead of vanishing, so the model can adapt; an absent/empty source is still skipped, and a `required` failure still throws. See `venue/docs/AGENT_CONTEXT.md`.

## [0.1.0] - 2026-06-12

The first release under the agreed versioning story (independent SemVer per
artifact; the platform version names the product generation). Companion
artifact releases: TypeScript SDK 1.5.0 (npm), Python SDK 0.2.0 (PyPI).
(Not exhaustive — see the git history for detail.)

### Added
- True cross-venue federation: `TwoVenueTestServer` and end-to-end cross-venue tests; `VenueHTTP` client contract tests against a real venue.
- Grid scheduler for deferred operation invocation; agent wake routed through it.
- Goal-tree agent improvements, including progressive ancestor compaction.
- Per-user secret bootstrap from venue config.
- Persistence resilience: periodic `fsync` sweep with `PersistenceHandler.flush()` bounding unclean-shutdown data loss; hard-kill / soft-kill resilience tests.
- Developer-experience scaffolding: developer-facing `README.md`, [`DX_PLAN.md`](DX_PLAN.md) public roadmap, `CONTRIBUTING.md`, `SECURITY.md`, this changelog, and a CI build-and-test gate.
- Issue and pull-request templates, Dependabot (Maven + GitHub Actions), and CodeQL scanning.
- A dedicated `publish-docker.yml` workflow — the single source of `ghcr.io/covia-ai/covia` image tags: `:latest` (develop), `:stable` (master), `:<x.y.z>` (release builds), `:<sha>` (every build).
- A stable venue tier (venue-1, venue-2) running the `:stable` image channel, deployed automatically from `master`.

### Changed
- Covia now depends on released **Convex 0.8.5** from Maven Central — a clean clone builds with `mvn clean install`, with no Convex source build. CI workflows no longer build Convex from source.
- Renamed `CLAUDE.md` to `AGENTS.md` (a `CLAUDE.md` import pointer remains).
- `GET /assets` response made consistent; no-limit paging fixed; `asset:list` scoped to the caller's own pinned assets.
- Documented a strong-consistency contract for `CoviaAdapter` CRUD, with regression tests.
- Logging moved off `printStackTrace`/`System.err` onto SLF4J.
- Hardened deployment JVM options and container health checks to prevent GC death-spirals.
- Refactored shared LLM-agent infrastructure into `AbstractLLMAdapter`.
- The Azure/EC2 deploy workflows now consume the published Docker image instead of each building and pushing their own.
- Documentation drift fixed: `BUILD.md` covers `covia-core` and the Convex prerequisite; `deploy/README.md` has a working Caddy install and release-based JAR download.
- Licensing clarified: the platform stays **EPL-2.0**; the SDK libraries (TypeScript, Python) are **Apache-2.0**.
- README build badge now points at the `Test` workflow (build + full test suite) instead of the snapshot build; the JAR download points at `latest-snapshot` until `0.1.0` ships.

### Fixed
- LangChain adapter now fails fast on a missing API key (#91).
- `covia_read` resolves Blob-keyed index entries by hex key.
- `agent:trigger`'s blocking wait is now cancellable; removed an unbounded status poll.
- Parallel test-suite races made deterministic.
